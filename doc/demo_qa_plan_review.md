# Demo API QA 実装計画レビュー

## 総評
- LangChain と LlamaIndex を併用したハイブリッド検索の全体像を段階的に整理しようとしており、retriever・パイプライン層・レスポンス組み立てを分離する方針は概ね妥当。
- ただし、既存 `structured_api` モジュール群との依存関係が複雑化する恐れがあるため、責務分割やインターフェース設計をより明示しないと再利用性とテスト容易性が損なわれる可能性が高い。

## 主要な指摘と改善提案

### 1. モジュール境界と依存関係の明確化
- `structured_api/demo_qa/retrievers/*` で LangChain/LlamaIndex を「再実装」すると記載されているが、両ライブラリの抽象化層を薄く包むだけなのか、完全に独自実装するのかが不明瞭。後者の場合はメンテナンスコストが高くなる。
  - **提案**: retriever ごとに共通の `BaseRetrieverProtocol`（インターフェースクラス）を定義し、LangChain/LlamaIndex のコンポーネントは DI で注入できる構成にする。これによりテストでのモック差し替えや他データソース拡張が容易になる。
- `structured_api/demo_api_qa.py` からの移設後も既存 CLI/設定と重複する恐れがあるため、`main_helper_0905.py` 等にある既存設定読み込みロジックとの整合性を再確認する必要がある。

### 2. レイヤ B/A のインターフェースとデータモデル定義
- B レイヤーの出力フォーマット（スロット候補の dict 構造）は概要のみで、スコア指標の種類・範囲が記載されていない。A レイヤーはこれを前提に正規表現等で抽出するため、仕様を固定しないと連携が破綻しやすい。
  - **提案**: `pydantic` などで `SlotCandidate`、`LayerBOutput`、`LayerAResult` を明文化。型に合わせてテストデータを作成し、入出力契約を守れるようにする。
- Neo4j のテンプレート選択（T1〜T6）について、選択基準が文章でしか説明されていない。状態遷移図や優先度テーブルを別途用意して開発者に共有すると保守性が向上する。

### 3. ハイブリッド検索統合の重複と実装手順の整理
- `run_hybrid_search` と `rerank_and_merge`、`compare_vector_graph` が計画内で二重に列挙されており、責務が曖昧。計画の段階でフロー図を描いて冗長性を排除すべき。
  - **提案**: フェーズごとに「入力→処理→出力」を 1 枚のシーケンス図で整理し、関数の最小責務を決める。`run_hybrid_search` はオーケストレーションに専念し、リランキングや比較は別ユースケースとして切り分ける。
- 並列実行やスコア正規化のアルゴリズム（MinMax、Z-Score など）の選択基準が書かれていない。検索ソースごとにスコア分布が異なるため、正規化戦略を事前検証しておく必要がある。

### 4. LLM 依存部分のコスト・レイテンシ対策
- クエリ正規化で `ChatOpenAI` を複数回呼ぶ構成だが、API コストやレイテンシ、レート制限に対するフォールバックが検討されていない。
  - **提案**: 生成結果をキャッシュする仕組みや、低負荷モード（LLM を使わず BM25 と単純形態素分析で補完）を設ける。また、LangChain CallbackManager を活用して LLM 呼び出しのトレースを記録する。
- クロスエンコーダー `ReRanker` の推論時間も考慮し、バッチ処理や上位 K 件のみリランキングする設定を `config.yaml` で調整できるようにする。

### 5. 設定とオペレーションの一貫性
- `.env` と YAML のマージ方針は記載されているが、優先順位や型変換ルール（例: 数値・真偽値の扱い）が未定義。混在すると予期せぬ型エラーにつながる。
  - **提案**: `config.py` で `pydantic-settings` などを採用し、バリデーションと型変換を統一する。CLI オプション > 環境変数 > YAML > デフォルト の優先順位を明文化。
- インデックス生成スクリプトの位置（`structured_api/demo_qa/tools/`）は妥当だが、生成物の保存先が `data/` 以下で固定されている。マルチ環境でのパス指定に対応できるよう CLI 引数や環境変数で切り替え可能にすると良い。

### 6. テスト戦略の具体化
- テスト計画は概念的であり、ハイブリッド検索のシナリオテストや LLM 呼び出しをモック化する方針が記されていない。
  - **提案**: retriever 層は「小さなダミーコーパスを用いた期待値テスト」、パイプライン層は「依存をモックしたフロー確認」、レスポンスビルダーは「テンプレート比較テスト」を最低限用意する。LangChain/LlamaIndex の API 呼び出しは VCR 的な記録再生またはスタブクラスで置き換える。
- デバッグログの検証方法（JSON ダンプが正しい構造を持つか）についても unit test を追加すると安心。

## 追加で確認したい点（必要ならユーザーへ質問）
1. 既存 `structured_api` には類似の retriever やパイプラインが存在するが、それらとの整合性や再利用計画はあるか。
2. Neo4j のテンプレート T1〜T6 の仕様詳細（入力スロット・出力フィールド・想定クエリ例）が揃っているか。ドキュメントがなければ早期に整備する必要がある。
3. demo データベース固有のスキーマやフィールド名に合わせたマッピング表を用意する予定はあるか。ハイブリッド検索時のフィールド整合性に直結するため確認したい。

## まとめ
- 全体構成は妥当だが、レイヤ間インターフェースと設定運用の詳細が欠けており、実装フェーズで摩擦が生じる恐れがある。まずはデータモデルと依存性の明確化、正規化アルゴリズムの検証、LLM コスト対策を優先的に具体化することを推奨する。
