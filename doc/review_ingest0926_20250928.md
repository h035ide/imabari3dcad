## 詳細指摘

- `api.txt` では全角スペースや全角記号が頻出し、`param_pat` の先頭一致が崩れている。`CreateSketchPlane` では `StyleName` 以降が JSON に存在しない。
- `_normalize_text` で `\u3000` を半角化し、Unicode 空白を許容する正規表現へ改修する必要がある。

### 3. COM/IDL 属性付き・裸パラメータの未対応
- `MirrorCopy`, `BodyDivideByPlanes` などに登場する `[in] BSTR plane` のような行はコメントが無く、`param_pat` ではマッチしないため JSON には `ReferMethod` しか残らない。
- `_parse_bare_param` 相当の短いヘルパーを導入し、属性付きパラメータも拾う必要がある。

### 4. 全角スペース＋括弧崩れによる欠損
- `CreateThicken`, `CreateOtherSolid` などではコメント前後に全角スペースが混ざり、補正ロジックが働かず `Sheet`, `ThickenType` など後半パラメータが失われている。
- 行末 `);` を含むケースに対し、括弧を除去した後に再パースする処理を追加すること。

### 5. パラメータオブジェクト定義の非対応
- `CreateBracketParam`, `CreateFacePlateParam` 等は列挙形式で記載されており、簡易パーサでは API エントリとして登録されない。

## 優先対応
1. `api.txt` 正規化（全角スペース統一・括弧前後の補正）と `param_pat` 拡張（Unicode 空白・ゼロ引数・括弧直後コメント対応）。
2. COM/IDL 属性付き・裸パラメータの抽出ヘルパー導入、行末 `);` への再解析処理追加。

## 補足
- 正規表現ベースのパーサでは例外処理が増え続けるため、`rule_parser.py` のような段階的パーサへ寄せる、あるいは構造化パースや LLM 補助による整合チェックを検討する価値がある。

## structured_api.json 仕様サマリ
- **ルート構造**: `checklist`, `type_definitions`, `api_entries` の3要素で構成する。
- **type_definitions**: `name`, `description`, `canonical_type`, `py_type`, `source.text` を保持し、ドメイン型と Python 型の双方を参照できるようにする。
- **api_entries**: `name`, `object_name`（または `category`）、`description`、`params[]`, `returns`, `source.text` を必須とし、`params[].metadata.position` で引数順序を管理する。
- **利用目的**: LLM や Chroma で文脈付きテキストとして活用しつつ、トリプル生成の正確性を高める基礎データとして活用する。

## 仕様トリプル生成の具体ステップ
1. **入力ソースの選択**: `structured_api.json` を基本入力とし、LLM による補強を行った場合は `llm_enhanced_docs.json` を優先する。両者は `api_entries[].source.text` に原文を含むため、抽出根拠を保持したまま処理できる。
2. **エンティティ整備**: 各 API エントリを `(:ApiMethod {name, object_name, description})` ノードに変換し、`params[]` の要素ごとに `(:ApiParameter {name, type, description, position})` ノードを生成する。戻り値は `(:ApiReturn {type, description})` として別ノード化し、`RETURNS` リレーションでメソッドと結び付ける。
3. **型リンク解決**: `type_definitions` 内の `canonical_type` と `py_type` を参照し、該当型が登録済みであれば `(:ApiType)` ノードへ `HAS_TYPE` リレーションを張る。未登録の場合は `extracted_triples` 側で警告し、後続のデータクレンジング対象とする。
4. **関係構築**: メソッドと引数ノードは `CALLS_PARAM`（仮称）で接続し、`metadata.position` を `order` プロパティとして保持する。既存の `CALLS` リレーションと混線しないよう、リレーション名またはラベルを明確に分離する。
5. **JSON 出力**: 生成したノード・リレーションを `api_spec_triples.json` として保存し、`sources.api_specifications` の配下に `nodes`, `relationships`, `metadata`（入力元ファイルパスやチェックサム）を記録する。これにより Neo4j ローダが `api` 系データだけを差分適用できる。
6. **検証フック**: トリプル化後に `api_entries` の件数と `CALLS_PARAM` リレーション数をカウントし、`structured_api.json` 側の `params[].metadata.position` と一致するかを確認する。欠損があれば `llm_enhanced_docs.json` を再参照し、原文テキストから回復を試みる。
